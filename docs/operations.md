# Эксплуатация

## Запуск приложения

В development используется `compose.yaml` совместно с `compose.override.yaml`. В production применяется `compose.yaml` совместно с `compose.prod.yaml` и production-переменными окружения. CI использует отдельный `.github/compose.ci.yaml` и не должен передавать его в рабочее окружение.

Перед запуском проверьте Compose конфигурацию, секреты и путь Dockerfile. Все конфигурационные слои должны ссылаться на один фактический Dockerfile. Текущие Compose/workflow-фрагменты ожидают `.docker/Dockerfile`; если файл хранится в другом месте, путь необходимо согласованно изменить.

## Smoke checks

```bash
docker compose ps
docker compose logs --tail=200 php database mailer
docker compose exec -T php php bin/console about
docker compose exec -T php php bin/console lint:container
docker compose exec -T php php bin/console doctrine:schema:validate
curl --insecure --fail --show-error https://localhost/api/docs
```

В образе FrankenPHP настроен healthcheck по внутренней metrics endpoint на `localhost:2019/metrics`. Успешный container healthcheck подтверждает доступность этого служебного endpoint, но не доказывает, что API, база и все зависимости функционально исправны; для этого нужны отдельные проверки.

## Логи и диагностика

```bash
docker compose logs --follow php
docker compose logs --tail=300 database
docker compose logs --tail=300 mailer
```

Не выводите в общий лог секреты среды, `DATABASE_URL` с паролем, приватные ключи или токены пользователей. Для диагностики конфигурации используйте `debug:config` с осторожностью и не прикладывайте к публичным issues вывод, содержащий секретные значения.

## MySQL

Перед миграцией дождитесь состояния healthy базы. Используйте имя сервиса `database` из сети Compose и внутренний порт `3306`. `localhost` внутри PHP-контейнера указывает на PHP-контейнер, не на MySQL.

Перед production-миграцией необходима резервная копия и оценка совместимости миграции с текущими данными. Для крупных таблиц отдельно оценивайте блокировки и длительность DDL-операций.

## Почта

Mailpit — исключительно dev-инструмент. В production задайте `MAILER_DSN` реального провайдера через секретное окружение, установите корректный sender и проверьте доменную аутентификацию почты у провайдера. Поведение при недоступности почтового провайдера, retry и observability должно быть определено для production отдельно.

## JWT и секреты

Приватный JWT-ключ, `APP_SECRET`, пароли БД и Mercure JWT secret не должны быть записаны в исходники, логи или общедоступные build artifacts. Настройте управление секретами и ротацию. CI-значения являются тестовыми placeholders и не пригодны для production.

## Backup/restore и отказоустойчивость

В текущей инфраструктурной конфигурации не описаны полноценная политика резервирования MySQL, disaster recovery, централизованный мониторинг, alerting и стратегия горизонтального масштабирования. Эти задачи должны быть закрыты до эксплуатации с требованиями к доступности данных.

План восстановления должен определить RPO/RTO, хранение резервных копий, доступ к ключам шифрования, проверку восстановления и порядок повторного применения миграций. Периодически выполняйте восстановление в изолированном окружении.

## Обновление и откат

Перед обновлением зависимостей или production image:

1. Пройти CI на release commit.
2. Прочитать changelog runtime, Symfony и Doctrine.
3. Проверить миграции на копии данных или staging.
4. Сделать backup, если затрагивается схема/данные.
5. Опубликовать и развернуть версионированный image.
6. Проверить healthcheck, API docs, login и основной ticket workflow.
7. Зафиксировать результат и план отката.

Откат контейнерного образа не гарантирует обратимость миграции БД; миграции должны оцениваться как отдельная часть релиза.
