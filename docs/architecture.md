# Архитектура

## Архитектурная цель

Приложение организовано как Symfony backend с HTTP API. API Platform отвечает за публикацию ресурсов и описание операций, Doctrine — за персистентность, Symfony Security — за аутентификацию и авторизационные правила, а инфраструктурный запуск обеспечивается FrankenPHP/Caddy и Docker Compose.

Это не набор независимых микросервисов. В текущем варианте backend и его основные бизнес-сущности работают в одном Symfony-приложении и используют одну MySQL-базу данных.

## Границы компонентов

### HTTP/API слой

`src/ApiResource` содержит классы, задающие публичные ресурсы и схему ответа. `src/ApiInput` содержит входные DTO и правила валидации. Конфигурация API Platform определяет форматы, пагинацию, OpenAPI и обнаружение ресурсов.

Публичный контракт не должен автоматически наследовать весь набор свойств Doctrine-сущности. Новые операции следует описывать явными входными DTO, выходными ресурсами и процессорами/провайдерами.

### Прикладные операции

`src/State/Processor` выполняет операции записи: создание тикета, изменение статуса, назначение исполнителя, добавление комментария, отметка уведомления как прочитанного и сценарии управления пользователями. `src/State/Provider` извлекает и проецирует данные для операций чтения.

Провайдер или процессор адаптирует запрос API, но не должен подменять полноценную бизнес-проверку доступа. Общие политики и сложные решения выносятся в сервисы.

### Сервисы предметной области и прикладной логики

`src/Service/Api/TicketAccessService` централизует правила доступности тикетов. `TicketStatusTransitionPolicy` проверяет допустимость перехода статуса. `ApiPaginator` ограничивает и унифицирует параметры пагинации.

Сервис регистрации и управления учётными записями `UserOnboardingService` обрабатывает регистрацию, подтверждение email, токены действий пользователя и приглашения. `UserActionMailer` отвечает за почтовые сообщения соответствующих процессов. `AuthRateLimit` инкапсулирует ограничения частоты для сценариев аутентификации.

Сервис, который меняет бизнес-состояние, должен быть точкой координации согласованной операции. Контроллеры и API-ресурсы не должны самостоятельно строить сложные транзакции или дублировать правила доступа.

### Доменная модель и персистентность

`src/Entity` содержит Doctrine-сущности. `src/Enum` — типизированные значения статусов, приоритетов, видимости комментария и уведомлений. `src/Repository` содержит специализированные запросы к базе.

Идентификаторы сущностей основаны на Symfony UID UUID и Doctrine `uuid`. Базовые mapped superclasses содержат общий код UUID и временных меток и не создают самостоятельные таблицы.

### Инфраструктура

- FrankenPHP исполняет PHP-приложение.
- Caddy обслуживает HTTP/TLS и интеграцию с конфигурацией приложения.
- MySQL 8.4 хранит состояние приложения.
- Symfony Mailer доставляет почтовые сообщения.
- Mailpit перехватывает почту в локальном development-окружении.
- Doctrine Migrations эволюционирует схему данных.
- GitHub Actions проверяет код и собирает production-образ.

Mercure-переменные присутствуют в Compose-конфигурации. Наличие этих переменных само по себе не означает, что все сценарии реального времени реализованы и проверены; наличие публикации событий нужно подтверждать конкретной реализацией и тестами.

## Типовой сценарий записи

При записи API Platform валидирует входной DTO, после чего вызывает соответствующий processor. Processor получает текущего пользователя из Security-контекста, вызывает прикладные сервисы и репозитории, проверяет разрешённость операции, изменяет сущности и сохраняет результат. Для аудируемых изменений состояние тикета, запись истории и другие обязательные данные должны фиксироваться согласованно.

Почтовые сообщения и внешние события не должны публиковаться до фиксации транзакции. Для гарантированной доставки событий при нескольких компонентах или повышенных требованиях используйте transactional outbox; текущая конфигурация сама по себе не доказывает наличие outbox.

## Типовой сценарий чтения

API Platform выбирает provider, который проверяет контекст пользователя и запрашивает разрешённый набор записей. Репозиторий отвечает за SQL/Doctrine-запросы, а provider формирует результат ресурса API. Коллекции используют пагинацию, а параметр `itemsPerPage` ограничен сверху значением 100.

## Правило расширения

Новый сценарий следует добавлять на соответствующий уровень:

1. DTO и API Resource — только если операция является частью публичного HTTP-контракта.
2. Processor — адаптация входной операции и координация use case.
3. Service/Policy — бизнес-правила, транзакционные границы и повторно используемые решения.
4. Repository/Entity/Enum — хранение и доменная модель.
5. Migration — любое изменение физической схемы БД.
6. Tests — проверка поведения, прав доступа и граничных случаев.

Не создавайте универсальные CRUD-операции для чувствительных сущностей, если они обходят бизнес-инварианты, управление жизненным циклом или аудит.
