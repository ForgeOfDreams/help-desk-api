# Аутентификация и авторизация

## Аутентификация

Приложение использует Symfony Security и LexikJWTAuthenticationBundle. Вход выполняется через
`POST /api/auth/login` по email и паролю. Защищённые HTTP-запросы передают access token через
`Authorization: Bearer <JWT>`.

Текущая JWT-конфигурация задаёт срок действия access token в 900 секунд (15 минут). Refresh-token
flow в описанном наборе компонентов не реализован. После истечения срока клиенту потребуется
повторно пройти аутентификацию, если отдельный механизм обновления токена не был внедрён.

JWT подписывается ключом из `config/jwt/`. Приватный ключ не должен попадать в Git, Docker build
context, логи или образы в открытом виде. Production-ключи передаются через secret store,
управляемое монтирование файлов или другой защищённый механизм окружения.

## Проверка состояния аккаунта

`UserChecker` блокирует отключённые и мягко удалённые аккаунты. Аутентификация не должна считаться
успешной только потому, что криптографическая подпись JWT корректна: состояние пользователя и
разрешения на конкретную операцию проверяются сервером.

## Роли

- `ROLE_USER` — обычный пользователь, работающий со своими обращениями.
- `ROLE_AGENT` — сотрудник поддержки с доступом к разрешённой очереди, командным тикетам и
  назначенным обращениям.
- `ROLE_ADMIN` — административные полномочия, включая обзор всех тикетов и приглашение
  пользователей.

Иерархия ролей, конфигурация firewall, порядок `access_control` и значения в таблице `roles` должны
быть согласованы. В Symfony `access_control` использует первое подходящее правило; публичный login и
другие публичные операции должны быть объявлены раньше общего правила защиты `^/api`.

Клиентские route guards и role claims токена не заменяют серверную авторизацию. Для каждой операции
требуются проверки прав, владельца, команды и видимости связанных объектов.

## Ограничение частоты

Конфигурация входа ограничивает неудачные попытки авторизации: 5 неудачных попыток за 15 минут.
Сценарии регистрации и пользовательских токенов также используют rate limiting.

Ограничитель Symfony сам по себе не защищает от объёмного сетевого DoS: запрос уже дошёл до
приложения. Для production необходимы rate limit на reverse proxy/CDN/WAF. При нескольких репликах
приложения лимиты должны использовать общий backend, например Redis, иначе локальное состояние
каждого процесса/контейнера может различаться.

## Регистрация и пользовательские токены

Публичная регистрация создаёт неактивную учётную запись, не выдаёт привилегированные роли и не
раскрывает существование email. Ответ `202 Accepted` используется с общим сообщением.

Токен подтверждения email:

- действует 24 часа;
- предназначен для одноразового использования;
- в БД сохраняется только SHA-256-хеш токена.

Токен приглашения/установки пароля действует 48 часов. После успешного использования аккаунт
получает установленный пароль, подтверждение email и активное состояние. Повторная выдача токена
того же назначения инвалидирует ранее активный токен. Операции потребления токена используют
транзакцию и блокировку, чтобы не допустить двойного использования при параллельных запросах.

Пароли хешируются через `UserPasswordHasherInterface`. Текущая проверка смены пароля требует указать
текущий пароль. Документация сценария задаёт длину нового пароля от 12 до 1024 символов и
ограничение 4096 байт UTF-8.

## CORS

`CORS_ALLOW_ORIGIN` должен содержать только доверенные frontend-origin. Не следует включать wildcard
origin в production. CORS не является механизмом аутентификации и не заменяет проверку полномочий на
сервере.

## Секреты и чувствительные поля

Не логируйте и не возвращайте:

- открытые пароли и password hash;
- JWT и приватные ключи;
- токены подтверждения/приглашения;
- SMTP-пароли, database credentials и `APP_SECRET`;
- внутренние заметки и данные аудита, которые не положены текущему пользователю.

Публичные пользовательские DTO не должны позволять клиенту задавать `roles`, `isActive`,
`emailVerifiedAt`, `passwordHash` или `deletedAt`. Создание первого `ROLE_ADMIN` выполняется
доверенной CLI/deployment-командой, а не публичной регистрацией.

## Пароль и действующие JWT

Смена пароля не отзывает немедленно ранее выданные JWT. При текущем TTL старый access token может
оставаться действительным до истечения 15 минут. Для немедленного отзыва нужен отдельный механизм,
например версия токена или denylist, с ясной моделью масштабирования.

## Будущие security controls

До production-эксплуатации необходимо отдельно подтвердить хранение приватных ключей, политику
ротации, централизованные rate limits при горизонтальном масштабировании, восстановление после
компрометации и актуальность всех авторизационных тестов.
