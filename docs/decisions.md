# Инженерные решения

Это краткий перечень действующих проектных решений. Он не заменяет ADR с номером и историей
обсуждения, но фиксирует основания и последствия решений, которые должны сохраняться при изменении
системы.

## Использовать Symfony-монолит с API Platform

**Решение:** бизнес-функциональность размещается в одном Symfony-приложении, а внешний контракт
предоставляет API Platform.

**Причина:** единая модель безопасности, транзакций и миграций упрощает работу с тикетами, историей
и уведомлениями без необходимости согласовывать несколько сервисов.

**Последствие:** модули отделяются логически через ресурсы, сервисы и репозитории. Разделение на
микросервисы рассматривается только при появлении конкретных требований к независимому
масштабированию или развёртыванию.

## Использовать явные API DTO-ресурсы

**Решение:** не публиковать Doctrine-сущности как универсальные writable API-ресурсы.

**Причина:** публичный контракт должен контролировать доступные поля, валидацию, права и семантику
операций.

**Последствие:** для операций записи используются входные DTO и processors; для чтения — providers и
выходные resources. Изменение внутренней сущности не должно автоматически менять API.

## MySQL 8.4 и Doctrine Migrations

**Решение:** использовать MySQL 8.4, utf8mb4 и миграции для контроля схемы.

**Причина:** воспроизводимый deployment должен переносить схему через ревьюемые изменения.

**Последствие:** schema changes генерируются/проверяются миграциями. CI применяет их на отдельной
тестовой базе и валидирует Doctrine schema.

## UUID и PHP backed enums

**Решение:** использовать UUID как ID и backed enums для фиксированных наборов значений.

**Причина:** UUID позволяет не раскрывать последовательные идентификаторы, а enum обеспечивает
типизированные значения в PHP без привязки доменной модели к MySQL ENUM.

**Последствие:** учитывайте бинарное физическое представление UUID в MySQL и обновляйте миграции,
валидацию, API и тесты при изменении enum.

## Централизованная авторизация тикетов

**Решение:** доступ к тикетам определяется текущим пользователем, его ролью, назначением и командой;
чтение внутренних заметок ограничено сотрудниками поддержки.

**Причина:** доступ к данным обращения должен быть защищён на сервере независимо от
пользовательского интерфейса.

**Последствие:** добавление endpoint не должно обходить `TicketAccessService` и соответствующие
проверки; тесты должны включать отказ в доступе к чужому тикету и внутреннему комментарию.

## Транзакционный аудит

**Решение:** изменения состояния тикета сопровождаются audit/history записями в согласованной
транзакции.

**Причина:** история должна соответствовать зафиксированному состоянию данных.

**Последствие:** не публиковать внешние события до commit. При требовании гарантированной доставки
внедрить outbox.

## Локальная почта через Mailpit

**Решение:** в development почтовые сообщения принимаются Mailpit, а в тестах используется null
transport.

**Причина:** локальные сценарии проверяются без отправки на реальные адреса.

**Последствие:** production должен передавать свой `MAILER_DSN`; конфигурация Mailpit не переносится
в production.

## Короткоживущий JWT без refresh flow

**Решение:** access token имеет TTL 15 минут; refresh token не входит в текущий контракт.

**Причина:** описанная конфигурация ограничивает время жизни bearer credentials.

**Последствие:** клиенту нужно повторно аутентифицироваться после истечения TTL. Требование
постоянной сессии потребует отдельного решения с refresh token, хранением, ротацией и CSRF-моделью.

## Форматирование в CI

**Решение:** PHP форматируется PHP-CS-Fixer с `@Symfony`; проверки выполнения идут в application
container, а repository-level lint выполняется Super-Linter.

**Причина:** PHP-specific checks должны соответствовать версии runtime и расширениям
`composer.lock`.

**Последствие:** не смешивать включение/исключение validators в Super-Linter v9. Все Composer
scripts должны быть доступны в том окружении, где вызываются.
