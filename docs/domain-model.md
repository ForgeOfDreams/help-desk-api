# Модель предметной области

## Основные сущности

### Пользователь и доступ

- `User` — учётная запись, email, хеш пароля, состояние активности и подтверждения email.
- `Role` — роль приложения; стандартные роли включают `ROLE_USER`, `ROLE_AGENT` и `ROLE_ADMIN`.
- `Team` — команда поддержки.
- `TeamMember` — участие пользователя в команде с датой вступления и ролью в команде. Эта связь
  является отдельной сущностью, так как имеет собственные атрибуты.

Связь пользователей с глобальными ролями представлена отношением many-to-many. Коды ролей в БД и
иерархия Symfony должны быть согласованы до назначения ролей аккаунтам.

### Тикеты

- `Ticket` — обращение с автором, статусом, приоритетом, категорией, назначением и командой.
- `TicketCategory` — категория обращения; поддерживает иерархическую организацию.
- `TicketComment` — комментарий к тикету с уровнем видимости.
- `TicketAttachment` — метаданные вложения и `storage_key`; не хранит содержимое файла в самой БД.
- `TicketWatcher` — подписка пользователя на тикет.
- `TicketHistory` — аудит действий и структурированных изменений.
- `TicketStatusHistory` — история переходов статуса.
- `TicketNumberCounter` — источник уникального публичного номера тикета.

### Уведомления

- `Notification` — уведомление пользователя.
- `NotificationDelivery` — сведения о попытках/состоянии доставки по каналам.

### Токены действий пользователя

- `UserActionToken` — токен одноразового действия, используемый для подтверждения email и завершения
  приглашения/установки пароля.
- `UserActionTokenPurpose` — тип действия, к которому привязан токен.

## Значения перечислений

`TicketStatus` содержит `new`, `open`, `in_progress`, `pending`, `resolved`, `closed`.

`TicketPriority` содержит `low`, `normal`, `high`, `urgent`.

`CommentVisibility` содержит `public`, `internal`.

`TeamMemberRole` содержит `member`, `lead`.

Для уведомлений используются `NotificationType`, `NotificationChannel` и
`NotificationDeliveryStatus`.

Эти значения реализованы как PHP backed enums и хранятся строковыми колонками. Изменение набора
enum-значений требует проверки сериализации, валидаторов, фильтров, миграций и клиентов API.

## Идентификаторы и временные метки

Сущности используют UUID через Symfony UID и Doctrine type `uuid`; в MySQL представление UUID
бинарное. Базовые mapped superclasses предоставляют общий идентификатор и временные метки. Они не
должны мигрировать в отдельные таблицы.

## Инварианты тикетов

- Создатель тикета определяется аутентифицированным пользователем. Клиент не может назначить
  произвольный `requesterId`.
- Пользователь видит только собственные тикеты, доступные ему по правилам API. Сотрудник поддержки
  видит тикеты, назначенные ему, относящиеся к его команде, а также нераспределённые тикеты общей
  очереди; администратор видит все тикеты.
- Изменение статуса проходит через `TicketStatusTransitionPolicy`. Статус `closed` считается
  терминальным в текущей политике.
- Назначение исполнителя должно проверять бизнес-ограничения, включая принадлежность к команде, если
  это требуется правилом приложения.
- Внутренние заметки доступны только сотрудникам поддержки и не должны попадать в представления
  обычных пользователей.
- Изменения статуса, назначение и другие важные действия должны создавать необходимые записи
  аудита/истории.
- `Ticket::version` использует optimistic locking для обнаружения конкурирующих обновлений одного
  тикета.
- Публичный номер тикета выдаётся атомарным `TicketNumberCounterRepository::nextValue()`; нельзя
  заменять его небезопасным `MAX(number) + 1`.

## Инварианты комментариев и уведомлений

Авторизация чтения комментария определяется доступом к соответствующему тикету. Публичные
пользователи не могут создавать внутренние заметки и не должны получать их через коллекции или
item-endpoint.

Чтение и обновление уведомлений выполняется в контексте их получателя. Отметка уведомления как
прочитанного должна быть идемпотентной.

## Аудит и чувствительные данные

`TicketHistory` хранит структурированные изменения в JSON. Аудит не должен содержать пароли,
приватные JWT-ключи, токены действий, Bearer-токены или тела комментариев, если только отдельное
утверждённое требование не определяет безопасную модель хранения.

Мягкое удаление не скрывает данные автоматически на уровне Doctrine. Все read-запросы и проверки
доступа должны явно учитывать `deleted_at`, где это применимо.
