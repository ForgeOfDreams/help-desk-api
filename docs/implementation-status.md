# Реализация и ограничения

Документ разделяет известное поведение и области, которые нельзя считать завершёнными только по
имеющимся конфигурациям и описаниям пакетов.

## Описанные функциональные области

- JWT login и защищённый API.
- Регистрация с подтверждением email.
- Повторная отправка подтверждения, приглашение сотрудника, установка начального пароля и смена
  собственного пароля.
- Пользователи, роли, команды и членство в командах.
- Тикеты, категории, комментарии, внутренние заметки и watcher-подписки.
- История статусов и аудит изменений.
- Уведомления пользователя и запись о состоянии доставки.
- Пагинация API и фильтрация списка тикетов по статусу/приоритету.
- Development Mailpit и CI для проверки Composer, PHP, Symfony, Doctrine, PHPUnit и API docs.

Наличие исходников/описаний для этих возможностей не является доказательством полного end-to-end
прохождения тестов на целевой инфраструктуре. Проверяйте текущее состояние CI и тестового набора.

## Явно не считать реализованным без отдельной проверки

### Refresh token

Описанный JWT flow выдаёт короткоживущий access token, но endpoint обновления токена в контракте не
определён. До внедрения отдельного refresh flow клиент должен повторно проходить вход по истечении
срока действия токена.

### Хранение вложений

`TicketAttachment` содержит метаданные и `storage_key`, но само содержимое файла не хранится в
MySQL. API загрузки, скачивания и безопасного доступа к объектному/file storage не считается
завершённым. Перед реализацией нужно определить provider, ограничения размера и типов, антивирусную
проверку при необходимости и авторизацию скачивания через доступ к тикету.

### Production mail

Mailpit предназначен для локальной разработки. Адрес реального SMTP/API-провайдера, retries,
мониторинг доставки, SPF/DKIM/DMARC и стратегия обработки отказа должны конфигурироваться отдельно
для production.

### Outbox и внешние события

Конфигурация содержит Mercure-переменные, но из одних переменных нельзя заключить, что публикация
событий реализована или гарантирована. Для гарантированной публикации после фиксации транзакции
требуется outbox или эквивалентная надёжная схема.

### Масштабирование rate limiter

Локальный Symfony RateLimiter не становится общим автоматически при нескольких репликах. Для
распределённого deployment требуется общий storage, например Redis, и протестированная конфигурация.

### Backup/restore и мониторинг

Политика backup/restore, централизованный мониторинг, alerting, SLO/RPO/RTO и проверенные runbooks
не определены приведёнными конфигурациями. Их следует описать и проверить до production.

### Бизнес-администрирование

В текущем описании API присутствует приглашение пользователей, но не универсальный CRUD для ролей,
команд и категорий. Не следует предполагать наличие административных HTTP-операций, если они не
зарегистрированы в фактической OpenAPI-схеме.

## Проверки перед утверждением статуса

Для каждой возможности должны существовать как минимум:

- endpoint/resource или CLI entrypoint;
- проверки авторизации на владельца/роль/команду;
- валидация входных данных;
- тесты положительного и отрицательного сценария;
- корректные миграции, если затронута схема;
- документация контракта и эксплуатационных зависимостей.

Изменяйте этот документ при завершении функциональности, добавляя ссылку на конкретный endpoint,
сервис, migration и тесты.
